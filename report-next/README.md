# LSD Report Next — next-gen HTML report UI

**Living Sequence Diagrams** competitor-style report shell (Vite + TypeScript, custom interactive SVG).

Tracks [#356](https://github.com/lsd-consulting/lsd-core/issues/356). Lives in-repo under `report-next/` as an **isolatable** Vite/TS package so packaging (next SemVer major of `lsd-core` vs sibling repo) can stay open.

**Status:** parallel engine / UX bar — **not** wired into the default Java report path. PlantUML + Handlebars remain the production default until an explicit opt-in / migration lands.

Related: Option A shell refresh (#355); embed assets (#354); hide participants (#79).

## Stack choices

| Layer | Choice | Why |
|-------|--------|-----|
| Tooling | **Vite 7 + TypeScript** | Fast local DX; `base: './'` for `file://` / CI artifact drops |
| Runtime | **Vanilla TS** (no React/Vue) | Tiny shipped JS; reports stay self-contained; no framework tax in the jar later |
| Diagrams | **Custom SVG** from domain events | Full CSS/a11y control, clickable message hits, activations, notes, dividers — no PlantUML / Mermaid runtime in the browser |
| Colour | **OKLCH tokens** + dark/light | 2026-default perceptual colour; system preference + `d` toggle |
| Overlays | **`<dialog>`** | Native focus trap / Esc; replaces CSS `:target` hash overlays |
| Typography | Geist → system-ui fallback | Product feel when online; readable offline via system fonts |
| State | In-memory filter/selection | Spike-sized; maps cleanly to a future Preact/lit island if needed |

PlantUML remains **optional** for production migration (server-side fidelity). This spike deliberately does **not** depend on it so the UI can evolve without golden SVG churn from the PlantUML engine.

## What’s demonstrably better vs current `lsd-core`

Compared to `lsd-core` main / Option A shell refresh:

| Capability | lsd-core today (incl. shell refresh) | This spike |
|------------|--------------------------------------|------------|
| Sequence look | PlantUML mono SVG | Custom SVG with participant cards, activation bars, duration chips, glow-on-hover |
| Message detail | CSS `:target` hash overlays | Modal `<dialog>` + copy payload + type/from→to pills |
| Navigation | Sticky chips + jump menu | Sidebar + status histogram + `j`/`k` keyboard nav |
| Search | Scenario title filter | Title + description + facts |
| Theme | Light-only GitHub-ish tokens | Dark-first + light + persisted preference |
| Mobile | Improved in Option A | Sidebar collapses to grid; toolbar wraps; diagram scrolls horizontally |
| Offline chrome | CDN d3 / hljs / mark.js (unless embed #354) | No diagram CDN; fonts optional |
| a11y | Partial | Focus rings, `aria-pressed` / `aria-current`, Tab onto messages, reduced-motion |
| Feel | Test-report artifact | Product UI you’d book as a “report experience” |

Honest gaps vs production PlantUML today: sprite includes, component diagrams, `newpage` split, short arrows, full colour/skinparam fidelity. Those are migration work, not spike goals.

## Migration path thoughts

### A. Domain model reuse (recommended first production step)

Keep capturing API (`LsdContext`, `Message`, participants, facts, metrics) stable.

Add a **report DTO** (JSON or embedded `<script type="application/json">`) emitted beside or instead of Handlebars HTML:

```
SequenceEvent* → ReportJson { scenarios, participants, events, dataHolders }
                 → lsd-report-next shell (static assets in jar / jsDelivr)
```

- Handlebars becomes a thin shell loader (or disappears).
- Approvals shift from full HTML+SVG bytes → **structural JSON** (+ optional screenshot smoke).
- PlantUML can remain as an alternate `renderer: plantuml | next` flag during transition.

### B. Full rewrite of report pipeline

Replace PlantUML + Handlebars with custom SVG (this spike) as the only engine.

- **Pros:** Drop `plantuml-mit` weight; one visual language; responsive layout / hide-participant (#79) become tractable.
- **Cons:** Major version; consumer golden wave; parity matrix (activations, notes, component diagram, newpage).
- **When:** After a feature-parity spike and an opt-in flag proves adoption.

### C. Hybrid

- Custom SVG for **sequence** (interactive).
- Keep PlantUML for **component** diagrams until a second renderer exists.
- Option A chrome can ship now on `lsd-core` without blocking this track.

### Suggested sequencing

1. Ship Option A on `lsd-core` (responsive chrome, low risk).
2. Stabilize a **ReportJson** schema from existing domain (no UI rewrite required).
3. Embed this shell as `lsd.core.reportEngine=next` experimental.
4. Decision gate: custom SVG vs keep PlantUML+postprocess vs Mermaid — based on parity + jar size + mobile readability.

## Isolation / packaging (open)

- **Not** on the Gradle classpath or default report writer — CI for the Java/Kotlin path is unchanged.
- `node_modules/` and `dist/` are gitignored; run `npm install` locally to develop.
- Packaging decision still open per #356: next major of `lsd-core` vs sibling (e.g. `lsd-ng-core`). This folder can later ship as report assets either way.
- Does not change or replace PlantUML rendering on `main`.

## Non-goals (this first check-in)

- No npm publish / no consumer API break  
- No PlantUML parity matrix completion  
- No JVM ReportJson emitter yet (sample data is hand-authored TS)  
- No flip of the default report engine

## Pitch (one paragraph)

**LSD Report Next** is a dark-first, keyboard-native report experience with custom interactive sequence SVGs — built to make Living Sequence Diagrams feel like a 2026 product, not a 2018 HTML dump. It reuses the lsd-core *domain ideas* while leaving the PlantUML/Handlebars pipeline behind so diagram UX, theming, and accessibility are no longer capped by a server-side markup engine.
